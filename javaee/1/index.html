url servlet


dns 查名服务类似于spring微服务里面的Nacos服务发现，也是一个服务对应的IP地址。不过它提供了更多的类似于负载均衡，动态上下线，查看健康状况等等的功能，更加智能。

HTTP或者https协议都是一问一答的形式，没有问就没有答，服务器没有保存上下文的信息。所有的内容都应该包含在request里面


符合javaee规范的servlet容器组件规范。服务端把请求request和响应发送到servlet基类，然后会调用service接口。HTTP servlet实现了这个基类就可以重写其中的doget dopost等等方法，这部分是自己的代码，把内容写到响应response， servlet再把这个响应送到前端服务器去响应渲染出一个页面。用的比较多的符合Java EE规范的servlet容器是tomcat，或者可以使用jetty。
使用规范的好处是，如果想要更换容器的话不需要再重新写这些接口的方法。


servlet对象只有一个，每一个请求都会用一个单独的线程去跑这个对象没有属性，因为线程会共享对象的属性会造成冲突 。 read的过程就是TCP的数据包拼接，decode把接收到的网络数据包分成一个Java对象，computer是自己service方法的处理逻辑。
但是线程不能无限制地增长，会受到内存CPU的限制。可以事先用线程池，线程池就是一个限制了可以使用的最大线程数，多于这个最大容量就会等待；如果超过了限制的等待时间，那么就会被拒绝。同时还会在预先的时候分配一定的孵化线程，有需求的时候就拿出来用。
还需要分析任务是io密集型还是CPU密集型，如果是io密集型，那可以多开线程消耗内存会比较大，但是CPU用的不是很多；如果是CPU密集型，那么即使线程数开得很多CPU的上限也不能突破。

Mybatis

Mysql原理

关注的是大数据高并发的情况下Mysql里面的存储和逻辑结构：

  • 在物理结构之下实际的存储是分为tablespace segment extent和page，需要关注的是page里面包含了实际的表数据结构， page directory可以根据要查找的主键进行二分查找快速查询。 page之间是一个双向链表的关系，page directory是单链表结构

这里要做一个区分，在逻辑结构下索引的存储叶子节点存放了实际的记录，也就是page。但是在物理结构之下，索引同样存放在物理的page下，它的索引是每一个页的最小主键值。根据要查找的所主键，找到存放的页的号码，根据这个页的号码，去extent找到对应的页，page directory二分查找目标主键值。这也是为什么叫做聚簇索引，把索引值和实际的记录绑定在一起。

page directory是定长的，我们要让这个数量中和一下。如果page太小，那么磁盘读出来的数据转一圈也很少，会有寻道时间的损失。
从磁盘当中根据索引读出来记录也是一个page，这是磁盘转一圈读到的数据大小，把它放在内存之后会根据哈希索引保存key value下次要查询某一个主键直接去读对应的value就可以了
做辅助索引会产生比主键递增索引更多的插入分裂（因为辅助索引的插入都是随机的，大概率还是在中间插入）。所以仅在必要的外键上面做辅助索引，如果要查询特殊的名称的话，就不要在关系型数据库里面做。这里也注意，如果要做查询的话一定要有索引

中间插入节点可能会使节点分裂，设置主键自增在最后插入数据才是减少分裂的最好插入方式，只会影响最后一页
删除节点更麻烦，它可能是中间某一层的分割节点。需要重新合并，实际上做的是逻辑的删除不是物理的删除

这个图还是比较清楚的，把创建readview和update记录的db_trx_id进行比较就可以实现读问题
mvcc多并发版本读，解决了多个事务开启下的读问题，但是不能解决写，写还是互斥的。undolog链历史记录在所有的依赖事务结束之后会被删除，在创建记录的事务被提交之后打上history标记。

spring 微服务

原则


单一职责：一个微服务解决一个问题，但实际业务开发采用了一个领域之间的松散耦合程度来判断是不是可以聚合成一个微服务。
松散耦合：采用轻量级通信（RESTful API 调用服务之间的功能）
独立存在：独立数据结构和数据库，每一个微服务都可以有自己的数据库（Mysql，Oracle……），甚至redis

为什么不一个微服务只用两张表或者三张表？
对象之间没有办法关联了，面向对象发挥不出威力，职责不能分配给对象，最后是面向功能设计（也就是微服务的单一职责，减少协作）。相对地使用领域建模ddd

各个模块之间采用RESTful API方式（严格保证单向通知，不能出现双向调用）或者使用消息通知机制（RabbitMQ……）来实现通讯

  • 集中配置：同一个服务的配置文件只放在一个集中的机器上面，其他相同服务机器只需要根据这个机器的application.yaml文件改配置。包括生产的配置文件里面都有密码，要把配置文件放在集中配置的机器上面，不能公开；以及定时刷新更换配置
  • 客户透明：服务之间的调用要发现、上线，不能采用IP的方式，需要有一个透明的管理，只需要服务模块的名字就可以
  • 负载均衡和容错：返回服务负载比较小的机器
